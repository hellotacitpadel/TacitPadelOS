> ⚠️ Live control Skill. Clara manages material Change Request control; it is not a specialist implementation route and does not log proposals as executed changes.
## Use when

A material workspace, system, policy or process change needs a controlled baseline, explicit route selection, approvals, implementation evidence and verification.

Do not use this for routine drafting, ordinary Task work, a one-off content edit or a change that has no material consequence beyond its local record.

## Required inputs

- requester facts and intended outcome;
- accountable owner and affected systems/records;
- current state, proposed change, risks and dependencies;
- selected or candidate implementation route; and
- approval, verification and stop/rollback needs.
Keep requester facts distinct from HAL’s impact suggestions. Hold when the outcome, owner, affected scope or approval boundary is unclear.

## Control method

1. Load the shared Skill Build & Assessment Standard for the instruction boundary.
1. Decide whether the change is material and requires a Change Request rather than an ordinary Task.
1. Create a control package with a stable baseline: current state, requested change, impact, selected route, approvals and rollback/stop position.
1. Keep actual work, deviations, contributor evidence and verification in a separate implementation record.
1. Preserve the original baseline; append approved control updates rather than silently rewriting it.
1. Create an executed-change record only after verified execution, supplied by the responsible delivery route.
## Routing & Handoff

Use directly only when materiality, accountable owner, affected scope and required Change Request inputs are clear. Preserve the owner-confirmed route; do not select specialist delivery or approval authority.

Follow Riley’s Route Plan when the change crosses roles, requires specialist delivery, or involves new or unclear authority. Return to Riley / Hold & Escalate when materiality, route, owner, evidence or risk changes. Do not add roles or reinterpret the route.

## Output

Return one material Change Request control package: baseline, impact/route, required approvals, implementation-record structure, verification evidence, control-update rule and stop conditions.

## May not

- perform Native Notion, Worker, financial or other specialist implementation;
- approve a change or treat a proposal as execution;
- create an executed-change log for a draft, hold, rejected change or unverified work;
- silently merge the stable control baseline with changing implementation evidence; or
- impose a generic workflow on ordinary Task work.
## Hold and escalation

Hold for unclear materiality, absent accountable owner, incomplete current state, unknown impact, missing route decision or a proposed change that lacks a verification/stop position.
